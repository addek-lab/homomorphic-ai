I. Chillotti, M. Joye, P. Paillier · Zama · v0.2.1, Oct 2020

The only source with full methods, parameters and benchmarks. Shows 20-, 50- and 100-layer networks running on encrypted MNIST digits, without retraining the model.

FROM THE ZAMA PAPER

Core concepts, in the order that makes them click

1. The service model

The setting is machine-learning-as-a-service. The user encrypts input x, the server evaluates its model hθ on the ciphertext, and the user decrypts. Correctness is the homomorphic property:

h(Encrypt(x)) = Encrypt(h(x))
Decrypt(h(Encrypt(x))) = h(x)

2. Noise is the real constraint

Every known FHE scheme produces noisy ciphertexts, and each operation increases the noise. Past a threshold the result can no longer be decrypted. A scheme that supports a fixed noise budget is called leveled. Leveled schemes can only run shallow circuits, which for neural networks means a moderate number of layers.

3. Bootstrapping refreshes the noise

Gentry's key idea (2009): homomorphically evaluate the decryption circuit to reset a ciphertext's noise. It turns a leveled scheme into a fully homomorphic one. Early bootstrapping took minutes; Ducas and Micciancio (2015) brought it to sub-second, and that line of work led to TFHE.

4. Programmable bootstrapping (PBS)

The paper's core contribution. The bootstrapping step can also apply any function, stored as a lookup table in a "test polynomial", to the encrypted value while it resets the noise. This is how non-linear functions such as ReLU become exact rather than approximated, and why depth is no longer a hard limit.

5. Which layers are cheap?

  • Leveled (cheap): dense, convolution, addition, flatten, average pooling. Weights are in the clear, so it's only multiplication by constants and additions.
  • Needs PBS (expensive): ReLU and other activations, and max-pooling.
  • Max-pooling trick: max(x,y) = y + ReLU(x−y), so a pool over k values costs k−1 PBS.

6. No retraining

Earlier work (CryptoNets, 2016, replaced ReLU with squaring; iDASH winners used leveled schemes) reshaped the model to suit the encryption. This paper keeps the original model and topology, which matters when you can't access the training data or a regulator must re-approve a changed model.

Read with care: this is a 2020 result on a small, easy dataset. It shows feasibility and the shape of the trade-offs. It does not predict the cost of a modern large model, and newer libraries and hardware are faster.

FROM THE KRUMAN AND TYMON PAPERS

HE is one layer, not the whole defence

Both industry papers argue for combining techniques. Kruman's headline view: federated learning is the most deployment-ready, differential privacy its natural complement, and HE should be reserved for high-security cases such as fraud detection or medical diagnosis.

TechniqueProtectsMain costMaturity (Kruman)
Homomorphic encryptionData while it is computed onCompute, memory, ciphertext sizeHighest security, hard to deploy
Federated learningRaw data stays where it isCommunication, non-IID dataMost deployment-ready
Differential privacyIndividuals in outputs / trainingAccuracy lost to added noiseHigh, complements FL
Secure multi-party computationInputs across partiesNetwork rounds, complexityHigh security, efficiency issues
Confidential computing (TEEs)Data in hardware enclavesTrust in the chip vendorFast; often quicker than HE (Tymon)
Synthetic dataTraining / test data exposureFidelity of the generated dataComplementary

Where HE joins the others

  • Secure aggregation in federated learning: encrypt model updates so the server never sees an individual one.
  • Hybrid pipelines: run only the most sensitive fields (e.g. national ID numbers) under HE; process the rest normally.
  • Selective in-use encryption: protect data in transit and at rest everywhere, in-use only where policy demands it.

What HE does not stop

  • Model inversion and membership inference: attacks on a trained model's outputs or parameters.
  • Data reconstruction from gradients in federated setups.
  • Data poisoning by a malicious participant.
  • Kruman's defences for these are DP noise, secure aggregation and Byzantine-robust aggregation.

CRITICAL READING

Claims I'd double-check before repeating

Claim (source)My assessment
"Bootstrapping can cause latencies 1,000 to 1 million times higher, making encrypted ML take days instead of hours." (Tymon)Out of line with measured data: a 100-layer network ran in about 11–24 s on a server at 80-bit security (Zama, 2020). Generalizes worst-case, older numbers.
"A 256-bit addition takes ~200 ms in HE vs 100 ns in plaintext." (Tymon)No source or scheme given, so it can't be checked. Cost depends heavily on scheme, parameters and batching; treat as illustrative only.
"Bootstrapping times under 10 ms for boolean operations"; ciphertext expansion of 25,000× or more; keys of gigabytes. (Kruman, citing a NIST presentation)Plausible for optimized TFHE-style schemes and for large parameter sets respectively, but these figures describe different schemes. Don't combine them into one system profile.
"Speedups of 10×–100× in the coming years" and "5–10×". (Tymon)Two different forecasts in one paper, with no stated basis. Forecasts, not results.
Market size: privacy-preserving tech $3.1B (2024) → $12.1B (2030), 25.3% CAGR (Kruman); HE ~$0.2–0.4B (2023), 8–20% CAGR (Tymon).Different scopes (all privacy tech vs HE only), so they don't contradict each other. Both come from market-research reports, not measurements.

SYNTHESIS

A realistic adoption path

Combining Tymon's four steps with Kruman's phased roadmap and the Zama benchmarks.

  1. STEP 1

    Find the sensitive flow

    Map where data is decrypted today. Start where privacy risk is highest: PII, IP, regulated records.

  2. STEP 2

    Pick a small model

    Logistic regression, small CNNs and tree models are the proven range. Quantize and test accuracy first.

  3. STEP 3

    Prototype and measure

    Build a sandbox on your own data. Record latency, memory, ciphertext size and the accuracy gap.

  4. STEP 4

    Layer and scale

    Combine with FL, DP or TEEs where it makes sense. Plan key management, monitoring and compute scaling.

Kruman suggests ~2–3 months for the "foundation" phase (encryption, DP and FL infrastructure). That is the paper's own estimate, not a measured figure.

Glossary

LWE / RLWE / GLWE
Learning With Errors and its ring / generalized variants. The hard problems that FHE security is based on; believed resistant to quantum attacks.
Leveled vs fully homomorphic
Leveled: a fixed noise budget limits circuit depth. Fully: bootstrapping lets the circuit run indefinitely.
Bootstrapping / PBS
Resetting ciphertext noise by homomorphically decrypting. Programmable bootstrapping also applies a function while doing so.
TFHE
Torus-based FHE with fast bootstrapping; works well for lookup-table style computation and ReLU.
CKKS
Approximate arithmetic on real numbers with SIMD packing; a common fit for linear-heavy ML.
BFV / BGV
Exact integer arithmetic schemes built on Ring-LWE.
Packing / batching
Placing many values in one ciphertext so one operation processes them all, which amortizes the cost.
Ciphertext expansion
How much larger encrypted data is than the original.
TEE
Trusted execution environment: hardware enclave (e.g. Intel SGX, AMD SEV) that decrypts data inside protected memory.
MPC · FL · DP
Secure multi-party computation · federated learning · differential privacy.
